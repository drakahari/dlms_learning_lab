# Account records, memberships and virtual ownership — foundation

Pure capability accepted after independent source review and main-checkout verification, checked2026-10-23. No authored account lessons, bundle registration or coverage promotion yet; engine/progress integration is documented in ACCOUNTS_BACKEND.md. `accounts` is an original in-process Rust module; no host account, filesystem, process, command, credential or clock API is called. Strings such as `/etc/passwd` refer only to derived simulated records.

## Why a separate model

Existing ordinary-user `filesystem::Tree` and original Unix seeds keep their users, progress and permission behavior. Their name-based IDs and owner-validity constraints cannot faithfully retain numeric ownership after an account is deleted. The account model instead has explicit stable UIDs/GIDs, one primary GID per user, distinct supplementary sets and numeric entry ownership. Group rename changes its name, retaining its GID and all numeric references. Orphan numeric owners/groups remain valid after deletion. Nothing couples these identities to existing process lessons or live sessions.

`State::new(Policy, Configuration)` validates its private state. Public records are constructors/data; mutating one does not mutate a State. `configuration()`/`policy()` return shared references. `apply(&Action)` uses bounded transactional preflight; `execute(line)` parses a supported request and applies it, or runs a read-only query. `parse` produces typed `Request` (including a name-bearing user-creation request resolved by State). Mutation success is silent with status0; typed errors distinguish invalid/unsupported/missing/conflicting/protected/limited operations. Error wording and all shadow-utils numerical failure statuses are not modeled. A missing keyed getent record specifically returns2 with no output.

All import/goal callers must retain immutable authored initial State and call `valid_against(initial)`. Imported policy cannot authorize its own altered protection. This validates policy equality, protected users/groups/entries/skeleton data and retained original username-to-UID/groupname-to-GID pins. Standalone serde/`from_json` validates shape; it cannot authenticate a supplied initial fixture. No event/history authenticates completion.

Intrinsic lifecycle operations and authored-context pins are deliberately distinct. For example, plain `apply`/`execute` can delete an unprotected username, then create that free name at a different unused UID; the database is intrinsically valid, but that retained authored username now fails `valid_against(initial)`. Future engine/workspace adapters must never execute directly into their published state: clone the already-bounded current State, execute/apply on the candidate, then require `candidate.valid_against(immutable_initial)` before replacing the current state or saving/checking it. If either stage fails, discard the candidate and retain the exact previous state with a clear fixed-fixture identity diagnostic. Apply this to every command, import and reset/example boundary; validate initial/current context before cloning an imported candidate. Reset builds from the authored initial fixture. The accepted engine adapter follows this candidate-before-publication rule; see ACCOUNTS_BACKEND.md.

## Exact language

One command per submission, at most2048 UTF-8 bytes and32 tokens. Single/double literal quotes and empty quoted arguments work; quoted values containing a dollar sign/backtick/backslash in double quotes are rejected rather than expanded. No shell expansion, scripts, piping, redirection, separators, process invocation or implicit execution. Options precede one final username/group operand; permutations of the listed unique options work. Documented long equivalents are explicitly enumerated in code. No GNU option abbreviations, option=value or bundled short flags except `usermod -aG`.

Queries:

- `id [USER]`, `id -Gn USER`, `id -nG USER`: explicit local records; omitted USER is simulated root. Primary first, then remaining GIDs in numeric order; exact group priority/order elsewhere is not promised.
- `getent passwd [NAME_OR_UID]`, `getent group [NAME_OR_GID]`, `getent shadow [NAME]`: local database projections only, one optional key, numeric-ID enumeration order. `cat /etc/passwd`, `/etc/group`, `/etc/shadow` return the same read-only derived projections. The group member list describes explicit supplementary membership; primary membership resides in passwd. No NSS/network/backend selection.
- `cat PATH`, `ls -ld PATH`, `ls -l DIRECTORY`, `ls -ln DIRECTORY`: bounded read-only virtual entries. Listing intentionally uses permission/type, owner, group, text-byte-length and full canonical path, with no locale/date/link-count/full GNU listing claim. Numeric owner/group fallback works when a name was deleted. No flags beyond these forms.
- `show`: explicitly simulator-only snapshot with supplied fixture date and expiry metadata. No login/authentication inference.

Mutations:

- `groupadd -g GID GROUP`; `groupmod -n NEW_NAME GROUP`; `groupdel GROUP`. No allocation, GID change, force, group password or implicit private group. Removing a current primary group fails; otherwise supplementary references disappear and numeric entry ownership remains.
- `useradd -N -u UID -g GROUP [-G LIST] -d HOME -s SHELL (-m [-k SKEL] | -M) USER`. Explicit identity/primary/home/shell/home policy, empty comment and no expiry. Group names or existing numeric GIDs accepted. `-m` copies a supplied skeleton with new user/primary numeric ownership, preserving supported child modes; home0700. `-M` creates metadata only. Default skeleton is supplied `/etc/skel`. No automatic IDs, private groups, mail, logs, subids or distribution-default emulation. Typed `Action::AddUser` can also carry a validated comment/expiry from a declarative fixture.
- `usermod [-a] -G LIST USER`, `usermod -aG LIST USER`: replace versus append supplementary sets; duplicates in an input list normalize, empty quoted replacement clears them. Primary GID stays separate. Snapshot duplicates are rejected. No multi-operation combined usermod options.
- `usermod -g GROUP USER`: existing primary-GID change. Entries inside the existing owned home with the old primary GID change group, including a different UID's entry; other groups and outside entries stay unchanged. This follows the pinned manual's group-based rule, not an invented owner-only recursive rule. A missing home is allowed; a foreign-owned home is explicitly Unsupported atomically. Linux skips ownership adaptation there; the simulator does not pretend to model that broader case.
- `usermod -e DATE USER`: metadata accepts strict UTC YYYY-MM-DD or canonical positive epoch day; empty quoted text/-1 clears. No implicit password operation or shell/login change.
- `chown USER:GROUP PATH`: one existing virtual entry, both fields required; existing names/canonical numeric IDs accepted. Nonrecursive, contents/mode retained, no arbitrary owner allocation.
- `userdel [-r] USER`: delete the record; plain deletion leaves numeric ownership/home intact. `-r` removes only the validated owned home subtree, preserving outside files. No mail or processes exist here; no Linux busy-user/process-check fidelity is claimed. Primary group is retained (`USERGROUPS_ENAB=no`).

All homes are unique direct children of `/home` except protected fixture identities. Creating/adopting an already existing home is Unsupported. Shared/nested homes, migration, links, ACLs, xattrs, devices/mounts and special modes are excluded. Skeletons are supplied immutable virtual directories under `/etc`. Protected root/service records, roots/entries and skeleton contents cannot be changed directly or indirectly. A newly requested UID/GID still present in numeric entry ownership is rejected; this is an explicit simulator restriction against accidental orphan-data reassignment, not a Linux prohibition.

## Expiry metadata and no credentials

`EpochDay` is an original bounded proleptic Gregorian UTC calculation. Range1..2932896 maps1970-01-02..9999-12-31, with strict real calendar dates and normal leap/century rules. Ambiguous epoch day0 is excluded. No current-time API is used; supplied policy date is fixed. Comparing an expiry to that date returns only before/on/after. This is an exact metadata query, never “can log in”, account-service authorization or a PAM expiration decision. Future tasks may ask for a past-date range; no unverified real-login boundary is required.

Every shadow projection has9 fields and a literal `!` sentinel, empty password-aging fields and the optional account-expiry day. No password/hash/secret is present or accepted. Clearing expiry does not create credentials or enable a login. `passwd`, `chpasswd`, `usermod -L/-U`, password aging, `chage`, PAM, sudo/su/login, authentication and sessions remain unsupported. This distinction matters: password locking alone does not establish denial of every authentication method. Special-purpose system-account creation and full LPIC-1107.1 are not claimed.

## Bounds, decoding and current outcomes

Maximum32 users/32 groups/16 supplementary groups per user/256 entries. Human mutable IDs1000..60000; fixture-protected IDs may be lower. Namespace `[a-z_][a-z0-9_-]{0,31}`; canonical ASCII path128 bytes/depth8; comment80 bytes without control/colon; regular text64KiB per file/256KiB aggregate/no NUL. Up to8 skeleton roots and8 shell choices. State/outcome JSON input4MiB; query output32KiB. Bounded field visitors reject excess string lengths before owned copies; map visitors reject duplicate/excess keys before decoding another large value; text aggregate is checked while reading entries. Escaped JSON parser scratch is bounded by the input cap in `from_json`/`requirements_from_json`; applications must use those bounded entry points for untrusted text rather than arbitrarily large direct serde streams. Normal serde shape decoding still has collection/string limits.

Every module-generated Error retains at most512 UTF-8 bytes, preserving its kind and useful beginning/context with an ellipsis if cut. The retained message is a fresh small String allocation, so a parser's very large unknown-field/variant diagnostic does not retain multi-megabyte capacity in a future UI. Temporary serde error formatting remains bounded by the4MiB input limit; this is a retained-feedback bound, not a claim of zero transient parsing allocations. Synthetic80KB multibyte unknown-field/variant regressions cover both state and outcome decoders and preserve original input/state.

Private State is at most the validated shape; apply uses a bounded clone, skeleton copy and validation before external mutation. Counts, path depth/length and aggregate limits apply to the resulting state; failed copy or protected-record effects leave the original exact state unchanged. Compact/pretty maximum-shape/control-character escaping roundtrip tests cover the persistence ceiling. No guarantee of real filesystem transaction/rollback or arbitrary host behavior follows.

`Requirement` supports exact users/groups/entries/whole configuration, explicit user+UID/group+GID absence, absent paths and inclusive expiry ranges. `valid_requirements(initial, requirements)` checks types/known initial identity pins; whole expected configurations pass shared borrowed policy/configuration bounds validation before any bounded State clone, including directly constructed data that bypassed JSON decoding. `checks(initial,state,requirements)` also rejects mismatched policy/protection/current identity. Positive goals plus whole final Configuration preserve unaffected accounts/files and prevent a physical/data-deletion shortcut. `requirements_from_json` bounds input/count (maximum64). There is no command-count, string-to-success, elapsed-time or read-history condition. Alternative valid action orders and refresh queries can pass; wrong user/UID, incomplete changes and unrelated damage fail when the authored outcomes require their preservation. Pure capability supplies no completion/progress state.

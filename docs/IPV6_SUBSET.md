# IPv6 capability contract

Designed 2026-10-22 before dependent lessons. Implemented pure capability with nine Rust tests and774 prefix comparisons against Python ipaddress; no new objective or authored-lab credit yet.

Model a small, entirely in-memory graph of named devices, their up/down interfaces, links, one optional manually assigned unicast address/prefix plus a link-local address per interface, forwarding state and static routes. Route tables derive local entries and explicitly declared manual on-link entries from current interface state; assigning an address alone does not establish that a prefix is on-link (RFC5942). Static selection uses destination longest-prefix match before distance, with deterministic diagnostics for unsupported equal-cost ambiguity. A link-local next hop always has an explicit outgoing interface. The typed route-status inspector explains inactive interface/distance/off-link next-hop causes; no-route diagnostics include matching inactive-route reasons. A reachable ping needs both forward delivery and a return route; probes never access a real network.

Prefix arithmetic covers /0 through /128 without overflow; text parses through Rust's IPv6 value type, so equivalent compressed/expanded forms compare numerically. Address categories distinguish unspecified, loopback, IPv4-mapped, multicast, link-local, unique-local, documentation and other unicast ranges. Anycast cannot generally be inferred from address bits alone. No IPv4-style broadcast or blanket subtraction of two host addresses is applied to IPv6. Manual interface assignment in the first topology model supports documentation/ULA and conventional fe80::/64 link-local addresses; other ranges remain classification-only rather than pretending full global source policy.

Links resolve an exact, currently up neighbor interface from typed addresses. Duplicate same-link addresses, down interfaces, off-link next hops, non-forwarding transit devices, missing routes, loops and return-path failure produce distinct diagnostics. This is a deterministic forwarding/adjacency model, **not** ND/DAD/RA packet exchange, SLAAC, DHCPv6, multicast forwarding, transport sessions, source-policy routing, ECMP, recursive static next hops, hardware timing or a complete router/Linux CLI. Source selection is deliberately one suitable interface address, with explicit scope for link-local probes; it is not a claim of full RFC6724 behavior. No learner terminal command will be advertised until its own supported grammar is implemented/tested.

Bounds: at most12 devices,8 interfaces per device,32 static routes per device and16 forwarding hops per path; bounded identifiers, no scripts or external resources. Invalid packs must fail before launch. Broken but structurally valid configurations must stay resumable and grade from current state. A capability-only commit must not change existing scenario IDs, progress schemas, approved workspaces or claim curriculum coverage.

Primary technical references checked 2026-10-22: [RFC4291 addressing](https://www.rfc-editor.org/rfc/rfc4291), [RFC4193 unique-local](https://www.rfc-editor.org/rfc/rfc4193), [RFC5952 canonical text](https://www.rfc-editor.org/rfc/rfc5952), [RFC4861 neighbor discovery](https://www.rfc-editor.org/rfc/rfc4861), [Cisco IPv6 addressing/basic connectivity](https://www.cisco.com/c/en/us/td/docs/ios/ipv6/configuration/guide/xe-17/ipv6-xe-17-book-cat8000/m_ip6-addrg-bsc-con.html), [CCNA v1.1 current blueprint](https://learningcontent.cisco.com/documents/marketing/exam-topics/200-301-CCNA-v1.1.pdf). Current CCNA1.8/1.9/3.3 remain planned/partial according to the actual authored crosswalk, separate from upcoming v2.0.

Address-category checks include the additional documentation block `3fff::/20` from [RFC9637](https://www.rfc-editor.org/rfc/rfc9637.html), checked against the [IANA special-purpose registry](https://www.iana.org/assignments/iana-ipv6-special-registry) (updated2025-10-09). These documentation ranges are virtual teaching labels, not real globally reachable network destinations. OtherUnicast means other address space, not a claim of global allocation/reachability. IPv6 subnet-router/other anycast assignments are not modeled; future authors must not use reserved anycast identities as ordinary workstation addresses. [RFC5942](https://www.rfc-editor.org/rfc/rfc5942.html) and [Cisco static IPv6 routing](https://www.cisco.com/en/US/docs/ios-xml/ios/ipv6/configuration/15-0sy/ip6-stat-routes.html) further bound this contract.

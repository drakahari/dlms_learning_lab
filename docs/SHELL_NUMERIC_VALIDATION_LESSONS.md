## Teach before testing

1. Ordinary characters0–9 are the accepted numeric alphabet. Brackets describe
   one position; `[0-9]*` means one digit followed by anything, not digits only.
   Learners can use an allowlist of exact widths or reject empty/non-digit/
   leading-zero/overlong text. Bound spelling and width before numeric tests.
2. Leading zero is a policy decision here because Bash arithmetic interprets
   octal-looking literals differently. Very large arithmetic can wrap. The
   deliberate tiny accepted ranges avoid both hazards before calculation.
3. Distinguish argument errors, invalid data that a script reports itself, and
   syntax/unsupported/resource diagnostics from the simulator. Expected status1
   in the audit is a correct handled result, not automatic lab failure.
4. Keep raw record text with the already taught `IFS= read -r` form; preserve the
   EOF-with-text case. Position advances independently of acceptance. Do not turn
   Unicode numerals, edge spaces, CR or shell-looking text into accepted numbers.
5. For publication, validate all data and total budget before the first write.
   A captured report is one supported method; a separate validation pass before
   ordinary printf is another. Restore one final LF after capture. Preview is
   equally validated and cannot change files.

The lab supplies arguments and virtual files; learners create working variables.
Usage strings name fictional script interfaces, not simulator-only commands to
invoke. The first example validates a locally created badge-slot value; it does
not show the assignment's attempts/delay solution. The second uses separate
crate-label files and a different accepted-width rule. The third previews a
room-capacity notice with separate source/output and a fixed example limit.

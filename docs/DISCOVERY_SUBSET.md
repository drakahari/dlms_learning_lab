# LLDP discovery capability contract

Specified 2026-10-23 before implementation. This is a native Rust, offline, typed capability foundation. It adds no lesson, terminal command, objective promotion or packet transmission. Existing catalog/coverage counts remain unchanged by this capability.

## Bounded model

The supported medium is a fixed Ethernet point-to-point attachment between two named device ports. Up to 12 devices, 16 ports per device and 96 links are supported, including disconnected ports. Every device has one unique locally assigned chassis ID; every port has a locally assigned port ID unique within its chassis. These represent the LLDP locally assigned identifier subtypes, not MAC addresses. Internal device/port/link keys are 1–64 lowercase ASCII letters, digits or hyphens. Advertised identifiers are 1–64 printable non-space ASCII bytes. Optional system name and port description are at most 80 printable ASCII bytes and cannot be blank when present. Duplicate display names are allowed; they are not identities.

Each port belongs to exactly one device and at most one link. Unknown endpoints, reused ports, duplicate link IDs, same-device links, duplicate chassis IDs and duplicate port IDs within a chassis are errors. Device cycles and separate links between the same device pair are permitted because advertisements never traverse a receiving port. No STP or data forwarding is inferred from this graph.

Configuration includes device-wide LLDP enable, per-port independent transmit/receive enable, port up/down, link up/down, and a device-advertised TTL of 1–65535 seconds. All booleans are explicit: no Cisco platform defaults are inferred. An advertisement is a typed action at the current simulated second. It contains the sender's chassis ID, port ID, TTL and optional system name/port description. Only the directly attached receiving port can record it. A disabled sender, disabled receiver, down port/link or disconnected port produces a typed delivery result, never invented command success. No remote information is copied across another link.

## Clock, cache and change semantics

Time starts at zero and advances only through an explicit positive or zero whole-second delta. Total supported time is 0–1,000,000,000 seconds; larger deltas or totals fail atomically. Advancing time ages records but does not send advertisements. Periodic scheduling, timer configuration, fast-start, reinitialization delays, transmission credit/rate limits and automatic advertisements on enable/config changes are deliberately absent. A future lesson must make this manual-event model clear.

A received advertisement creates or replaces the one neighbor record for that local port. Refresh resets its receive timestamp and expiry to receive time plus advertised TTL, independently of the receiver's configured TTL. A record expires exactly at that timestamp. Querying reports age, remaining TTL, current ability to receive from that peer, and whether its recorded fields match the current sender configuration. A still-unexpired cache entry is historical evidence; it does not establish current connectivity or current remote configuration. Queries do not refresh records. There is no wall clock, background thread, NIC, socket, shell or process execution.

The explicit shutdown action sends a typed TTL-zero withdrawal when normal transmit/physical/receive conditions permit; it removes the matching peer record. Shutdown does not disable configuration, so a subsequent advertisement can restore the record. Changing from effective transmit enabled to disabled sends a graceful withdrawal on the old live link if reception is still enabled in the new configuration. A simultaneously broken link/port cannot deliver that withdrawal. Local receive disable, global disable or loss of the local physical link clears that local port's cache immediately. This is the chosen simplified receive-module lifecycle; instantaneous local cache deletion is not claimed as universal IOS behavior. Remote advertised field/TTL changes stay historical until a refresh or expiry.

Runtime reconfiguration preserves the exact device/port keys, chassis/port identities and link IDs/endpoints. Link order and endpoint order have no significance. System name, port description, enable flags, up/down state and TTL may change. An invalid or identity-changing configuration leaves state untouched. A new physical graph requires a new simulation with an empty cache. This contract supports future native topology and port tables without allowing deletion, renaming or rewiring to pass an authored identity requirement.

JSON collections reject duplicate keys and excess entries; unknown fields and unsupported variants fail. The topology loader caps bytes at 256 KiB; the state loader uses a separate 1 MiB cap before deserialization. A snapshot repeats local/remote endpoint identifiers and advertisement strings in up to 192 records, so its bound must exceed the topology-only bound. Both limits cover canonical compact and pretty serde JSON for maximum legal structures, including worst-case escaping of printable ASCII string values. Arbitrarily padded JSON can still exceed these explicit input limits. Direct serde deserialization must still be preceded by a caller document byte cap; collection bounds cannot bound an arbitrary string allocation. Runtime state deserialization validates clock, cache limits, fixed peer identities, active local receive attachments, timestamps and duplicate cache entries. It permits historical optional fields/TTL. State restoration is structural validation, not authentication of historical events; future grading must query current configuration and preserve the authored identity separately.

The scalar text budget is at most 73,152 bytes in the topology plus 104,448 bytes in a full cache before JSON escaping. Printable ASCII needs at most two JSON bytes per character; field names, punctuation, numbers, booleans and canonical pretty indentation add fixed overhead for the bounded structures. The 1 MiB snapshot ceiling leaves ample room for that overhead. The regression fills all 12×16 ports/96 links and 192 records with maximum-length keys/identifiers/labels, every advertised text character needing quote/backslash escaping, TTL 65535 and ten-digit simulated timestamps. Its topology is 125,339 bytes compact / 150,434 bytes pretty; its state is 325,827 bytes compact / 387,044 bytes pretty. Both representations restore successfully. The original shared 256 KiB ceiling was insufficient for valid snapshots and is retained only for topology input.

## Declarative outcome requirements

Typed requirements are validated against an explicit authored initial topology. Every check validates that topology and the current state, then requires the entire current topology to preserve the initial device/port keys, chassis/port identities and physical attachments. A changed identity fails even when a superficially similar cache entry or configuration exists. Requirements do not authenticate event history.

`CurrentNeighbor` names one local port and its expected directly attached peer; validation rejects unknown, self, disconnected or wrong-peer requirements. It passes only with a cache entry for that peer whose remaining TTL is positive, whose current direct delivery is possible, and whose recorded identity, TTL, optional system name and optional port description match the sender's current configuration. Historical fields, an unexpired but no-longer-deliverable record, or an expired/absent entry cannot earn this outcome. Refresh is still an explicit action. `AbsentNeighbor` means no cached neighbor on the named local port, including historical neighbors; it is not a synonym for inability to receive a new advertisement. An existing historical record must expire or be withdrawn/cleared before this absence outcome passes.

`GlobalConfiguration` compares device-wide enable, advertised TTL and optional system name. `PortConfiguration` compares the whole named port, including physical up state, independent transmit/receive flags, optional description and pinned port identity. `Configuration` compares the entire expected topology/configuration; link and endpoint ordering remain insignificant. Expected port/whole-topology identities must agree with the authored initial topology, while expected operational settings may describe a repair. To preserve unaffected settings, use those initial global/port snapshots or an entire expected configuration. Current-neighbor and absence requirements alone do not imply configuration preservation; authors must include the relevant guards, particularly physical-up and unrelated-port/global settings for absence tasks. Global and port guards do not preserve Link.up. In particular, breaking a link can satisfy an absence outcome while all those granular settings remain unchanged. An absence task must therefore require the whole expected Configuration (which includes link-up state), or a positive current-neighbor requirement on that same attachment when that matches the task. A positive neighbor on some other link does not guard this one. A separate physical-link requirement is not implemented. Different repairs may satisfy a current-neighbor goal while explicit preservation guards remain unchanged.

Each requirement has bounded fields/collections inherited from the topology contract; its JSON loader caps input at 256 KiB and validates references/identities before it can be checked. Enclosing lesson/requirement collections must impose their own document and item limits during future integration. This foundation adds no engine, UI, persistence integration, assignments or coverage evidence.

## Explicit exclusions

No CDP, IOS parser/CLI emulation, real Ethernet frames, packet serialization/parsing, captures, NIC inspection, IP/ARP/ICMP, VLAN transport, bridge forwarding, STP, shared media, wireless/tunnels, LAGs, stacked devices, multiple LLDP agents/scopes or neighbors on one local port. No LLDP-MED, PoE, management addresses, system capabilities, system description, VLAN/PHY/organization-specific TLVs, TLV selection, malformed TLVs, counters, SNMP/MIB API, security/spoofing or full IEEE 802.1AB conformance. Chassis/port subtypes other than locally assigned are excluded. The in-process `matches_current` diagnostic uses simulator knowledge and is not an LLDP wire feature or a real-device guarantee. No issuer endorsement, hardware acceptance or complete CCNA objective 2.3 coverage is claimed.

## Primary references checked 2026-10-23

- [Cisco CCNA 200-301 v1.1 objectives, 2024](https://learningcontent.cisco.com/documents/marketing/exam-topics/200-301-CCNA-v1.1.pdf): current objective 2.3 includes both CDP and LLDP. This foundation supplies no authored evidence and no CDP support; upcoming v2.0 remains separate.
- [Cisco Catalyst 9600 Interface and Hardware Components Configuration Guide, IOS XE 17.18.x, LLDP chapter](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9600/software/release/17-18/configuration_guide/int_hw/b_1718_int_and_hw_9600_cg/configuring_lldp__lldp_med__and_wired_location_service.html): establishes separate global/transmit/receive controls and remote hold-time semantics. Platform timer/reinitialization behavior is excluded here. Optional management TLVs must not be confused with the protocol's mandatory identity/TTL fields.
- [David Law, IEEE P802.3at Layer 2 ad hoc, version 1.0, January 2008](https://www.ieee802.org/3/at/public/2008/01/law_1_0108.pdf): primary presentation quoting 802.1AB receive initialization, replacement/TTL refresh and shutdown construction. It supplies historical protocol rationale, not a current normative conformance claim.
- [Bottorff/Congdon, IEEE 802.1 LLDP for IETF LSVR, 2025-04-22](https://www.ieee802.org/1/files/public/docs2025/new-bottorff-lldp-tlvs-for-lsvr-0425-v00.pdf): primary overview of logical endpoint identity and advertised lifetimes. Its proposed router scopes/extensions are not implemented.
- [Paul Bottorff, IEEE 802.1 LLDP Between LSVR Routers slides, 2025-04-22](https://www.ieee802.org/1/files/public/docs2025/new-bottorff-lldp-for-lsvr-0425-v00.pdf), slides 3, 6–7 and 19–20: identifies mandatory chassis/port/TTL fields and locally assigned identity subtypes. This model narrows identity lengths/character sets further and deliberately omits the illustrated automatic transmission behavior.
- [Jetzt/Blatherwick/Dove, IEEE P802.3at LLDP/LLDP-MED Proposal for PoE Plus, 2006-09-15](https://grouper.ieee.org/groups/802/3/at/public/2006/09/jetzt_1_0906.pdf), slide 6: explains the basic non-forwarded, one-way, point-to-point discovery scope. Its PoE proposal is not implemented.

The tests cover directional controls, direct-link containment, refresh/exact expiry, shutdown, current invalidation, topology/identity preservation, malformed serialization and independent clock arithmetic. Native UI, persistence integration and authored lessons remain subsequent work.

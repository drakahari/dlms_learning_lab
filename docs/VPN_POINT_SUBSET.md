The finite syntax follows the OpenVPN 2.6 configuration reference, checked 2026-11-15:
https://openvpn.net/community-docs/community-articles/openvpn-2-6-manual/
That site also lists 2.7; 2.6 is an explicit reference, not a claim to be the latest.
Current LPI 201/202 objectives remain 4.5: 212.5 OpenVPN requires configuration and
point-to-point/site-to-site reasoning. Future Change Considerations are separate:
https://www.lpi.org/our-certifications/exam-201-202-objectives/

The modeled world has two supplied IPv4 UDP/TUN peers, reciprocal point-to-point
tunnel addresses, explicit destination routes and at most 16 virtual identity files.
ca/cert/key select supplied authority, validity, key-pair, purpose and name facts.
No PEM is parsed, signature verified, clock consulted or TLS handshake performed.
An absent optional purpose/name request is unevaluated, not verified. Future tasks
must distinguish these required security settings from logical transport readiness.

Supported directives: dev tun, proto udp/udp4, port, remote numeric-IPv4 [port],
tls-server/tls-client, ifconfig local remote, ca/cert/key virtual paths,
remote-cert-tls server/client, verify-x509-name NAME name, route network mask.
Scalar repeats, quoting/escapes, inline comments and all other directives fail
honestly. Whole-line #/; comments work. Configurations are capped at 8 KiB / 128 lines,
32 routes; virtual paths must be bounded ordinary names under /etc/openvpn/.
These are virtual lookups: no path, include, script, plugin or network is executed.

Every explicit supported route uses this point-to-point tunnel. Exact interval
unions compare all required destinations, accepting equivalent split/overlapping
routes and rejecting hardcoded sample hosts or an overbroad default. This is not
host routing, DCO, a multipoint server, push/iroute, TAP, IPv6, TCP transport, MTU,
firewall, DNS or cryptographic implementation. No real deployment/security proof,
full OpenVPN/exam coverage or new platform/novice acceptance is implied.

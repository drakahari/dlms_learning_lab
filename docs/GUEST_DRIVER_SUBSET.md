## Intended practical boundary

`guest_driver` composes the existing script-free RPM **metadata** model and finite
`kernel_modules` model. Represented guests are x86_64; that is an exercise fact,
not the architecture of the learner's computer. Supplied archives contain inert
module descriptors, not actual RPM or executable .ko bytes. No package scripts,
real dependency resolver, downloading, initramfs, boot or actual connectivity.

Source-owned facts declare at most16module objects,4devices,8local archives and
one repository snapshot. Object paths come from the module catalogue; the virtual
file universe must match those paths exactly. Each archive declares x86_64 and
ordinary, known descriptor payloads. Existing metadata dependency/transaction
rules apply. Unknown descriptors, changed object attributes, scripts, foreign
paths, source identifiers or oversized inputs must be refused honestly. Missing
objects are supported; arbitrary edited module binaries are not interpreted.

## Keep the important states separate

- A package record describes installed support; its object file can be missing.
- Installing/replacing/reinstalling a script-free supplied package changes virtual
  files. It does not secretly rebuild lookup or load a driver.
- `depmod -a` derives the simulated lookup from present current-release objects.
- `modprobe` uses that lookup and declared dependencies; `insmod` needs an exact
  supplied object and already loaded dependencies. Partial dependency loading on
  operational failure is retained rather than inventing atomic rollback.
- A loaded driver can outlive its object file. Repeating `modprobe` can therefore
  report success while a fresh unloaded request fails. Removing a package alone
  does not unload a driver or change the represented running kernel.
- A loadable driver for another adapter does not bind the supplied target device.
  Kernel-release compatibility does not prove the complete real ABI, signatures,
  firmware or hardware behavior; those are outside this finite model.

The new opt-in `execute_available` receives presence derived from caller-held
virtual files. Existing `execute` and `execute_named` keep their original object
universe, outputs and serialized runtime shape. Availability is not a new trusted
field in saved module state. A fresh-request observation uses a separate in-memory
copy with unloaded modules; it is explicitly not a boot test or host operation.

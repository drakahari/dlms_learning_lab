## Finite supported behavior

A supplied set of build-ready module source descriptions and kernel/header fixtures
has one declared architecture. Learners will inspect registration, built and installed
states per module/version/kernel. Build can register a missing supplied source;
install can register and build as needed. Manual add→build→install and direct install
must lead to equivalent resulting state. An omitted -k selects the supplied running
kernel, never the host kernel. A version handover uses explicit uninstall of the installed instance for the selected
kernel, followed by installation of the supplied replacement. Other kernels remain
unchanged. Automatic replacement/version sanity checking is not simulated.
Uninstall leaves the supported built record and source registration available.

Initial console grammar: dkms add/build/install/uninstall/status; module/version
or -m module -v version; optional one -k release for per-kernel operations/status.
Status can filter supplied module/version/kernel values. dkms -h/--help explains the
subset. Single literal operations only, bounded input and output. No shell quoting,
expansion, operators, paths/tarballs/RPMs, hooks, --force, --all, autoinstall, remove,
unbuild, signing, module loading or arbitrary dkms.conf/Makefile evaluation. An
uninstall without a currently installed instance is explicitly outside this initial
subset; refuse honestly rather than inventing error/no-op compatibility.

Supplied sources are already build-ready for the supplied kernel fixtures. This
model does not expose missing-header/compiler/ABI-failure cases until their partial
side effects can be implemented from authoritative behavior. Unknown/unavailable
fixtures are unsupported requests, not simulated real compiler failures. No fake
binary compilation, kernel API compatibility or loaded/working-device claim.

All module files are derived virtual inventory entries under a declared fixture
layout. An installed record means placement for one kernel, not module loading.
No host files, subprocesses, DKMS commands, headers, modules, package managers,
services, network or system changes. No dependencies or existing shell evaluator
changes. Bound supplied sources, kernels, registry pairs, text and status output
before exposing a workspace. Keep example and assignment state separate later.

The two lessons teach registration/build/install, explicit versus default kernels,

A harmless extra uninstalled build for a protected kernel is allowed: it neither
changes an original supplied record nor replaces an installed fallback. This
keeps an accidental build without -k recoverable without requiring unsupported
unbuild/remove commands. Changed original records or additional installed versions
still fail. A focused alternate-solution regression covers this distinction.
